How I Cut Oracle Query Times by 60% in Production

February 2026 · 6 min read

At Amdocs, I worked on the CRM platform powering JCOM — Japan's largest cable telecom operator with over 10 million subscribers. The system handled everything from billing to service activation, and performance was critical. When subscriber lookup queries started taking 12+ seconds, it became a priority to fix.

Here's what I learned optimizing Oracle databases in a live production environment.

Finding the Problem

The first step wasn't writing better queries — it was understanding why the existing ones were slow. Oracle's Automatic Workload Repository (AWR) reports became my best friend. AWR captures database performance statistics at regular intervals, giving you a clear picture of what's consuming resources.

The AWR data revealed three patterns: full table scans on subscriber tables with 10M+ rows, nested loop joins where hash joins would be more efficient, and PL/SQL procedures that were executing row-by-row instead of set-based operations.

Composite Indexes

The biggest wins came from indexing. Single-column indexes existed, but the queries filtered on multiple columns simultaneously. For a query filtering on region_id and subscription_status, having separate indexes on each column meant Oracle still had to merge results.

Creating composite indexes on the actual filter combinations eliminated this overhead. The key insight: index column order matters. Put the most selective column first — in our case, region_id had higher cardinality than subscription_status, so it went first. 

CREATE INDEX idx_subscriber_region_status 
ON subscribers(region_id, subscription_status)
TABLESPACE idx_ts;

PL/SQL Refactoring

Several stored procedures used cursor-based row-by-row processing — the classic "slow by slow" anti-pattern. A procedure updating subscriber statuses was looping through millions of rows individually when a single UPDATE with a WHERE clause would accomplish the same thing in seconds.

The refactored version used bulk operations with FORALL and BULK COLLECT where set-based operations weren't possible, reducing round trips between the PL/SQL engine and SQL engine.

Query Result Caching

Some queries ran identically thousands of times per day — subscriber plan lookups, for instance. Oracle's Result Cache stores query results in shared memory, so repeated executions return cached data instead of re-executing. 

SELECT /*+ RESULT_CACHE */ plan_name, monthly_rate, data_limit
FROM subscription_plans
WHERE plan_status = 'ACTIVE';

This worked well for relatively static data like plan catalogs. For frequently changing data, we used materialized views with fast refresh to pre-compute expensive joins.

Results

After implementing these changes across 20+ queries, average execution times dropped from 12s to 4.8s — a 60% improvement. The work was done incrementally over several weeks, testing each change in staging before production deployment, with zero downtime throughout the process.

Key Takeaways

Measure first. AWR reports, execution plans, and wait event analysis tell you exactly where time is being spent. Without measurement, you're guessing. Index strategically — composite indexes aligned with actual query patterns beat generic single-column indexes. Think in sets, not loops — PL/SQL procedures should minimize row-by-row processing. And cache what doesn't change — Result Cache and materialized views can eliminate redundant computation entirely.

Database optimization isn't glamorous, but when your queries serve 10 million subscribers, every millisecond counts.
